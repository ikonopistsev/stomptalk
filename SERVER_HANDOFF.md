# Ветка stomptalk-smid для серверного A/B

Цель этого этапа — закончить текущую библиотеку и измерить её влияние на сервер.
Пакетный быстрый путь, карты границ и дальнейшая смена модели отложены до
серверных результатов. Адаптер сервера делает серверная команда.

## Что подключать

C99 API: `include/stomptalk/parser.h`. Реализация C++14, static/shared CMake target
`stomptalk::stomptalk`. API несовместим со старым callback-интерфейсом. Установка
экспортирует только публичные C-заголовки. Пример полного цикла есть в README.md
и в `test/purestomp.c`.

```sh
cmake -S . -B build-server -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_C_COMPILER=/usr/lib/llvm/23/bin/clang \
  -DCMAKE_CXX_COMPILER=/usr/lib/llvm/23/bin/clang++ \
  -DCMAKE_C_FLAGS_RELEASE='-O2 -DNDEBUG' \
  -DCMAKE_CXX_FLAGS_RELEASE='-O2 -DNDEBUG' \
  -DSTOMPTALK_BUILD_AVX2_PARSER=OFF -DSTOMPTALK_BUILD_AVX2_NAMES=OFF \
  -DSTOMPTALK_BUILD_TESTS=ON -DSTOMPTALK_LIBRARY_INSTALL=ON
cmake --build build-server -j
ctest --test-dir build-server --output-on-failure
```

Пути compiler выше соответствуют этой машине; на другой машине указать её
Clang/Clang++. Для первого серверного A/B используем SSE2 без PGO и без AVX2;
сравнить также O3 в отдельном build directory. При add_subdirectory те же
compiler/optimization options задаются при конфигурации всего сервера.
Ветка библиотеки — `stomptalk-smid`; после получения зафиксировать commit SHA
в конфигурации зависимости, чтобы сравнение оставалось воспроизводимым.

Один parser и один заранее выделенный блок памяти на соединение. Сначала
config_default → get_memory_requirements → выделение с указанным alignment → init.
Память сохраняет адрес до destroy; освобождает её приложение. Размер нельзя
хардкодить. Настраиваются число результатов/заголовков, байты строк, лимит
заголовков кадра и тела. Defaults: 64 / 256 / 32768 / 64 / UINT64_MAX.

Бэкенды: 0 AUTO, 1 scalar, 2 SWAR, 3 SSE2, 4 AVX2. Проверять
`stomptalk_available_backends()` и фиксировать фактически выбранный
`stomptalk_parser_backend()` в отчёте. AUTO выбирает SSE2/scalar; AVX2 включается
явно, если доступен. Он сканирует заголовки по 32 байта с безопасным хвостом.
Известное тело пропускается по длине; для неизвестного используется memchr.
Нет глобального требования AVX2 к процессу. `STOMPTALK_BUILD_AVX2_PARSER=OFF`
исключает эту реализацию независимо от optional name classifier.

Если старые protocol utilities остаются рядом с v2, проверить конфликт
внутренних C++ имён `stomptalk::parser` и путей include. В существующей интеграции
1.8.0 сервер уже изолировал namespace; аналогичная изоляция может потребоваться
для v2. Подключать публичный C API, не внутренний parser.hpp.

## Критические правила адаптера

- Выполнять execute на оставшихся байтах; сначала обработать ВСЕ возвращённые
  записи, затем следующий execute. `consumed` нельзя подавать повторно.
  OUTPUT_FULL означает: обработать результаты и продолжить с остатка входа.
  NEED_INPUT допускает ноль результатов, а также уже опубликованные body-фрагменты.
- `frames[i]` — запись кадра/фрагмента, не обязательно отдельный полный кадр.
  BEGIN начинает кадр; COMPLETE означает проверенный конечный NUL. Одной
  достигнутой content_length для подтверждения COMPLETE недостаточно.
  Финальный фрагмент может иметь payload_size=0. Пустое тело даёт BEGIN|COMPLETE.
- Метод и все заголовки доступны на каждой записи. Достаточно обработать
  метаданные при BEGIN. `method_id` и `content_length` уже разобраны; их повторный
  разбор не нужен. Пары header key/value сохраняют порядок и дубликаты;
  значим первый content-length. Неизвестный метод имеет UNKNOWN и method_text.
- Views — pointer+size, без завершающего NUL. Они истекают при следующем
  execute/reset/destroy. Вход должен оставаться неизменным до обработки результата.
  Payload всегда ссылается на вход этого вызова и никогда не сохраняется parser.
  Нужные очереди/body-фрагменты копирует или обрабатывает потребитель.
- Ранее выданные body-фрагменты нельзя отозвать при ошибке в конце кадра.
  Завершение RPC/публикацию сообщения подтверждать после COMPLETE. При ERROR
  прежние полные кадры из того же результата доступны; ошибка sticky до reset.
- Escaping уже декодирован (кроме literal CONNECT/CONNECTED). Перед исходящим
  STOMP сериализатор должен снова экранировать ключи/значения. Это известное
  место несовместимости старого server sender с новым parser.
- `NULL,0` — пустой вызов, не EOF. При закрытии соединения NEED_INPUT означает
  незавершённый кадр/CRLF; транспорт решает, как его отклонить. Heartbeat — LF/CRLF,
  отдельные межкадровые NUL не принимаются.

## Сравнение на сервере

Основной контроль — реально используемая быстрая 1.3.1 (либо её точный commit),
плюс уже имеющаяся интеграция 1.8.0. Для v2 проверить SSE2 и AVX2 отдельно,
зафиксировать opt flags, хэши бинарников и адаптера. Не менять одновременно
header_store, очереди, сериализацию, libevent и клиентскую нагрузку.

1. Корректность: LF/CRLF, произвольное деление TCP, несколько кадров за read,
   escaping туда/обратно, бинарное тело и NUL внутри content-length, длина 0,
   пустые тела, финальный NUL отдельно, receipts, disconnect/reconnect,
   переполнение выходной порции, лимиты и неверный завершающий байт.
2. Нагрузка: исходный короткий RPC; больше заголовков; большие тела с/без длины;
   фрагментация. Одинаковое число завершённых RPC и полезные байты у вариантов.
3. Прогрев, затем минимум три чередующиеся пары без perf. RPC/s, p50/p95/p99,
   user/system CPU, число ошибок/таймаутов, RSS. Длительность/affinity одинаковы;
   не запускать benchmark или сборку параллельно с другим вариантом.
4. Отдельный perf процесса сервера: self и стеки, top 5 значимых функций;
   parser, adapter, header_store, allocator, очереди и libevent. Self-% — доля
   sampled user CPU, а не доля задержки RPC. Уменьшение процента без общей
   скорости и абсолютных CPU counters ещё не подтверждает ускорение сервера.

Существующие `stomperd-rpc/parser-profile/run.py`, `check_compat.py` и
`test_rpc.py` пригодны как основа после адаптации API. В старом профиле два
header-state цикла занимали около 24% sampled user CPU. Это исторический
ориентир, не доля всего parser и не прогноз новой скорости. Там интеграция
1.8.0 дала −3.59% RPC/s к 1.3.1 с адаптером — новый вариант должен сравниваться
и с этим старым быстрым путём.

Если full-server A/B почти не меняется, дальнейшее усложнение parser отложить
и смотреть горячие серверные операции. Если parser/adapter остаются значимы,
следующий изолированный опыт — прямо формировать несколько обычных пар
key/value, используя текущее дерево для escaping и переноса между буферами.
Это проверит цену прохода дерева; новый публичный API для опыта не требуется.

## Компилятор и профиль сборки

[Матрица четырёх версий](artifacts/version-matrix/README.md) содержит Os/O2/O3
для GCC 16.2.1 и Clang 23.1.4. На исходном C-тесте v2/SSE2, 100 млн кадров,
Clang O3 без PGO: 5.16 с; GCC O3: 6.66 с. Это ориентир для выбора серверных
сборок, не измерение RPC/s. Начать сравнение разумно с обычной Clang сборки.

[PGO GCC](artifacts/pgo-study/README.md) дал 6.74 → 6.08 с SSE2 в отдельном
парном прогоне, но ухудшил некоторые длинные/escaped сценарии. Clang PGO
ещё не проверялся. Для серверного PGO сначала собрать инструментированный
parser и прогнать реальную тестовую RPC-нагрузку, затем пересобрать с профилем.
Сохранять сетевой трафик для этого необязательно; запись нужна только для
повторного воспроизведения. Если пишем вход, сохранять порядок по соединению
и границы вызовов execute, включая фрагментацию и несколько кадров за вызов.
Повторный контроль делать также на нагрузке, не участвовавшей в обучении.
