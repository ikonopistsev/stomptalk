# Исходная antoull на 1–18 цифр — 28.10.2026

Сравнение с `c41715a`: удалена добавленная перегрузка
`bool antoull(uint64_t&, const char*, size_t)`. Для данного парсера не было
требования поддерживать 19–20 цифр или произвольно длинные префиксы нулей.
Используется прямой вызов исходной `int64_t antoull(const char*, size_t)` из 1.8.0.
Шаблонное вычисление и switch по длине совпадают с оригиналом.

Результат меньше нуля означает ошибку CONTENT_LENGTH. Принятая длина отдельно
проверяется против настроенного max_body_size. Ведущие нули входят в лимит
18 символов; это ограничение реализации, а не утверждение о синтаксисе STOMP.
Типы полей C ABI, потоковый payload и правила первого content-length сохранены.

У пустого значения finish_token возвращает NULL/0. Поэтому assert конвертера
теперь допускает эту пару; switch отклоняет нулевую длину без чтения памяти.
Дополнительной runtime-ветки для пустого значения не добавлено.

Тесты покрывают 1 ТБ, 1 ТиБ и 999999999999999999 байт: разбирается объявленная
длина и несколько байтов тела с продолжением, без выделения огромного payload.
Проверены предел 18/19 цифр, ведущие нули, нецифровые символы, guard page,
все границы фрагментации, настроенный лимит тела и пустое значение.

Проверки прошли: GCC 16 / Clang 23, Os/O2/O3; Debug; ASan/UBSan с assertions.
Каждая полная unit-сборка проверила 22272 потока и 4219922 условия. Ручной
libFuzzer: 245116 запусков за 31 секунду, без ошибок; новые seeds находятся
в fuzz/corpus/v2, их hashes — new-corpus.json.

Матрица производительности была избыточна для этой локальной правки.
По замечанию пользователя оставшиеся измерения остановлены; контрольные
повторы не запускались. Выигрыш скорости не заявляется. Обычные значения
content-length и раньше обрабатывались исходным шаблонным конвертером.

Полученные результаты сохранены в checks.json и commands.jsonl; status
фиксирует остановку. Во время основной матрицы менялась нагрузка компьютера
(заметно по GCC Os: 6,6 → 11,4 млн кадров/с внутри одной серии). Поэтому
абсолютные скорости нельзя непосредственно сопоставлять с прежними отчётами.
В свежей паре GCC O2/SSE2 получено 21,66 → 20,76 млн кадров/с; без запрошенного
ранее контрольного повтора причина этой разницы не установлена.

check.py сохраняет выполненный сценарий. Снимки build/before и build/after
не входят в Git; их содержимое фиксируют base_commit, source.patch и hashes
в checks.json. На измерениях использовались CPU 4, PIC, без LTO/PGO;
5 повторов purestomp с прогревом и чередованием, контроль полезных результатов.
24 формы/плана подачи и perf/GNU time выполнены частично: точные завершённые
команды и результаты перечислены в checks.json.

PGO переобучен отдельно через штатный cmake/ClangPGO.cmake, чтобы приложенный
профиль соответствовал изменённым функциям. Это проверка пригодности профиля,
а не новый замер производительности. Логи — pgo-O2.log и pgo-O3.log.

Оба независимо полученных O2/O3 профиля совпали побайтно; проверены
инструментированные и обычные profile-use сборки с unit/C99 тестами.
SHA-256 и точные параметры — pgo-metadata.json.
