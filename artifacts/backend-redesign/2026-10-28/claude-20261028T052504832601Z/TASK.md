# Независимое дизайн-ревью тезисов пользователя: stomptalk-smid → stomptal-smid-2

Ответь по-русски. Нужна независимая оценка обоснованности решения ДО реализации.
Не поддакивай автору кода или пользователю. Два критерия каждого решения:
**упрощение исходного/машинного кода** и **ускорение полного парсера**.
Не редактируй исходники, не выполняй команды, не связывайся с внешними сервисами.
Все входы в текущем каталоге — frozen snapshot для чтения. Вывод дай в final.

## Тезисы пользователя (приоритетные требования, часть формулировок дословная)

1. Почему backend/swar.hpp разбивает известный content-length на несколько
   сравнений по 8? «я думал это будет через конвертацию к uint64»,
   «почему memcmp не делать просто на всю известную длину?».
   Для SWAR константа должна быть обычной, без продублированных символов.
2. equal_ends8 выглядит лишним усложнением. Нужен минимальный интерфейс,
   «не надо много методов». Возможно один небольшой общий механизм для
   поиска и equal: оба используют сравнения и маски относительно размера.
3. «метод сравнения мы делаем через раскрытие шаблона с выбором версии sse swar».
   Для известного N версия равенства выбирается при компиляции.
4. Последнее уточнение: «сканнеру вообще не нужен шаблон он просто сканирует
   используя smid метод максимально пригодный для буффера»,
   «ну из вкомпилленых в реализацию».
   То есть обычная inline-функция, использующая доступную ширину;
   не предлагать пользователю еще один template API для scanner.
5. Обработка по нисходящей: AVX2 широкий блок, остаток меньшего размера —
   SSE2, затем SWAR/короткий хвост. «так же по нисходящей выбор идет на этапе
   компиляции». Список реализаций и прямые связи должны задаваться при сборке;
   размер реально доступного входа неизвестен до выполнения.
6. Макросом можно отключить AVX2, либо AVX2 и SSE2; тогда остается SWAR.
   AVX2 опционален: он не дал общего ускорения короткого purestomp относительно
   SSE2, хотя выигрыш есть на длинных полях.
7. «и в самом движке сравнения константа должна быть content-length они разные
   их две». Рабочая интерпретация Codex, ПРОВЕРЬ ее: одна обычная строковая/
   целочисленная форма для SWAR и одна безопасная SIMD-форма, пригодная также
   для 14-byte сравнения в AVX2-контексте. Не надо третьей избыточной копии.
8. Реализация после ревью — в отдельной ветке `stomptal-smid-2`.
9. Референс пользователя — **AVX-Memmove**, его автор тоже выбирал стратегию
   по длине. Проверь фактический код reference/avx-memmove/, а не предположения
   по названию проекта. Это источник подходов, библиотеку не подключать.

## Что уже установлено по текущему коду

- backend/swar.hpp::equal<N> уже вызывает один memcmp(data,text,N).
- Лишь equal_ends8<14> для специальной packed content-length использует два
  сравнения по 8. Строка content-length 14 bytes: [0..7] и [6..13], поэтому
  packed expected имеет 16 bytes и продублированные `t-`.
- Цель SSE2 упаковки — точное сравнение 14 bytes без 16-byte чтения за входом.
  Выравнивание expected не разрешает overread входа.
- scan.hpp содержит настоящий SWAR scanner: memcpy в uint64_t и has_zero.
  Это не тот же код, что equal в backend/swar.hpp.
- scan_avx2.hpp уже передает остаток <32 в SSE2 scanner; SSE2 затем идет прямо
  в scalar byte loop. У dynamic equal уже есть AVX2 → SSE2 → swar::equal;
  у fixed-size equal пути длиннее 32/64 сейчас передают остаток в SWAR.
- GCC16/Clang23 Os/O2/O3 assembly для packed / plain memcmp(14) / uint64 loads
  лежит в assembly/. На O2 два memcmp(8) не превращаются в два вызова libc.
  Clang plain и words дают одинаковый branchless XOR/OR код; GCC формы разные.
  Нельзя на этом основании объявить ускорение полного parser.

## Контекст и неизменяемые требования

Pure C ABI, caller-owned preallocated memory, no allocations/reallocations при
парсинге. Named tailcall state tree остается. Streaming payload не копируется,
метаданные должны оставаться корректными при любом разрезе ввода и OUTPUT_FULL.
Парсер семантически распознает только content-length. Отдельный расширенный
классификатор имен вызывается клиентом по желанию.
CPU + OS availability проверяются вне цикла, сейчас при init. Компиляция AVX2
сама по себе не делает его безопасным на процессоре без AVX2.
C API/backend forcing сохраняется; сейчас принудительный unsupported backend
дает ERROR_BACKEND. AUTO сейчас выбирает SSE2, иначе scalar. Пользователь хочет
SWAR при отключении SIMD — это изменение AUTO/конфигурации надо явно оформить.
Не путай build-time отсутствие backend, CPU capability и runtime длину диапазона.

## Особые вопросы, которые ревью обязано разрешить

A. Какой минимальный общий набор операций на блоках действительно оправдан
   для поиска и equal? Дай короткий псевдокод и число сущностей, без большого
   framework/иерархии классов. Может быть полезно разделять только конечную
   редукцию: первый event против всех равных байтов.
B. Текущий SWAR has_zero дает возможные дополнительные отметки после настоящего
   нулевого байта вследствие borrow. Для first-match на little-endian это было
   достаточно. Можно ли такую маску использовать как точную побайтовую маску
   равенства? Проверь контрпример x=0x0101010101010100. Если нет — предложи
   минимальное безопасное решение и его цену. Учти порядок байтов.
C. В какой мере шаблонное equal<N,Backend> и НЕшаблонный scanner могут
   разделять операции и гарантировать inlining? Нужны ли runtime indirect
   calls в сканировании? Можно ли оставить выбор CPU только при init?
D. Два представления content-length: что реально нужно SWAR/SSE2/AVX2?
   Достаточен ли plain memcmp(14) для SWAR? Где хранить константы, чтобы
   не навязать packed layout обычному сравнению и не засорить общий backend?
E. AVX-Memmove: точные файлы/строки, как выбираются размеры и обрабатывается
   остаток. Что можно заимствовать как идею? Что нельзя переносить напрямую
   (aliasing/alignment, baseline ISA, CPU dispatch, licensing)?
F. Чем отличается equality от поиска нескольких символов? memcmp не ищет
   разделители. Не подменяй scanner цепочкой повторных libc memchr по каждому
   событию: отдельный эксперимент уже показал высокую стоимость этого пути
   на коротких строках (около четверти CPU в libc memchr/PLT).
G. Какие compile configurations и correctness/perf тесты обязательны, чтобы
   проверить реальное упрощение/ускорение: AVX+SSE+SWAR, SSE+SWAR, SWAR only;
   размер 0/1/7/8/9/15/16/17/31/32/33, guard pages, misalignment, первый event,
   unequal byte at every position, overlapping packed constants, arbitrary
   fragmentation. SSE-disabled/AVX-enabled — поддержать или явно запретить?
H. Не требует ли требование scanner «максимально пригодный» уточнения:
   максимально широкий не всегда быстрее? Как сохранить опциональность AVX2
   и не обещать выигрыш без замера полного парсера?
