## 1. Вердикты

### Простота — **хорошо**

Иерархия `scalar → swar → sse2 → avx2` с наследованием вместо отдельных адаптеров понятна и читается линейно. `is_header<Backend>` как функтор с двумя перегрузками (шаблон по литералу, runtime по view) — чистая идея. `name_group` со статическим поиском дискриминатора устраняет лишний уровень маппинга. Разделение `content_length` (portable) и `content_length_sse2` (упакованный XMM-константа) явно и не смешивается.

Существенного сокращения объёма алгоритма нет: 2726 строк vs 2719 до, `.text` вырос на 834–5347 байт. Удаление `_`-хелперов — уборка исторического мусора, не упрощение живого кода; REVIEW.md это честно фиксирует.

### Корректность — **хорошо с одним наблюдением**

Явных багов не найдено. Ключевые точки проверены ниже. Одно место требует внимания (P1 — гипотеза, не подтверждённый баг).

### Скорость — **нейтрально, локальные регрессии не объяснены**

Общего ускорения нет. Регрессии в Os/SSE2 (+8.39%, spread 1.6%/1.6%), Os/AVX2 (+3.78%), O2/SWAR (+4.71%) выходят за пределы шума. Улучшения только в части O3-сборок. Топ функций (`hdrline_hdr_key` + `hdrline_val` ≈ 40–60%) не изменился. Объяснять регрессии конкретной инструкцией или I-cache без доказательств не следует; соображения в следующих разделах.

## 2. P0 / P1 / P2 замечания

### P0 — критические баги
**Нет.**

### P1 — существенные, требуют ответа перед серверным deployment

**P1-A: Нераскрытая причина Os/SSE2 регрессии**  
`evidence/README.md`: gcc16/Os/SSE2 −8.39% (spread 1.63%/1.58%), clang23/Os/SSE2 −4.62% (spread 1.63%/0.75%). Медиана превышает spread примерно в 5×, это не шум. `src/is_header.hpp` добавляет новый шаблонный путь и `is_content_length<B>` с `_mm_load_si128` на выровненную константу. При Os это может означать лишний load из холодной D-cache в узком цикле обработки заголовков. Это гипотеза — нужен `perf stat -e cache-misses` или аннотированный `perf record` на `hdrline_hdr_key` до/после.  
**Конкретная точка:** `src/is_header.hpp:34` + `src/backend/sse2.hpp:62–67`. Если окажется что `content_length_sse2` добавляет cache miss, fallback на scalar `is_content_length` в Os-сборке обоснован.

**P1-B: `STOMPTALK_BACKEND_AVX2` в `boundary`-проверке — различный паттерн**  
`src/parser_impl.hpp:239–248`:
```cpp
const bool boundary =
    state_ == &parser::start_state<STOMPTALK_BACKEND_SCALAR> ||
    ...
    || (backend_ == STOMPTALK_BACKEND_AVX2 && state_ == avx2_state())
```
Все остальные backends сравниваются только через указатель состояния. AVX2 дополнительно проверяет `backend_`. Это корректно (avx2_state() возвращает одно значение), но хрупко: если когда-нибудь AVX2 будет иметь несколько стартовых состояний (пример: один для LF, другой для CRLF), условие тихо сломается. Это гипотетический риск, не баг сейчас. Стоит документировать инвариант.

### P2 — средние, желательно исправить

**P2-A: `is_header` default template = `backend::swar`**  
`src/is_header.hpp:9`: `template<class Backend = backend::swar>`. Внутренний код должен явно передавать `B`, но если кто-то использует `is_header<>()` без параметра на AVX2-машине, получит SWAR. Поскольку это internal helper — не ABI-проблема. Документировать намерение.

**P2-B: `name_group::select()` без static_assert при провале дискриминатора**  
`src/name_group.hpp:47–64`: если не удаётся найти 1- или 2-байтный дискриминатор, возвращается `{size, size}` и классификация молча деградирует до линейного перебора (через `find` с `key(data) == 0`). Для текущего словаря STOMP это не проблема, но при расширении протокола регрессия будет незаметной.
```cpp
static_assert(select().first != size || sizeof...(Rest) < 2, "no discriminator found");
```
Сейчас нельзя добавить этот static_assert напрямую (select() вызывается в constexpr контексте без прямого диагностирования), но можно добавить проверку через вспомогательный constexpr bool.

**P2-C: SWAR big-endian fallback непроверен**  
`src/backend/swar.hpp:84–88`: `break` без проверки правильности `p` не теряет позицию (scalar начнёт с текущего `p`), но путь не тестируется ни одним тестом и не покрыт fuzz-корпусом. На x86 это dead code, но сохранять его нужно правильно.

**P2-D: `equal<0>` через memcmp с nullptr**  
`src/backend/swar.hpp:26–28`:
```cpp
template<std::size_t Size>
static bool equal(const char* data, const char* text) noexcept {
    return Size == 0 || std::memcmp(data, text, Size) == 0;
```
При `Size == 0`: `0 == 0` = true, memcmp не вызывается. Это корректно, но вместе с `is_header`:
- `is_header({nullptr, 0}, "")` → `0 == 0 && equal<0>(nullptr, "")` → true  
Пустая строка-литерал `""` имеет `Size=1`, поэтому `name.size == 0` — true, `equal<0>` — true. Пустой ключ заголовка совпадает с `""`. В STOMP-парсере пустые ключи отклоняются раньше (`if (*p != ':' || !token_.size)`, `parser_states.hpp:97`), но тест на граничный случай отсутствует.

**`src/parser_avx2.cpp` — нужен.** Он является target-контекстом для `#pragma GCC target("avx2")` / `#pragma clang attribute push`. Изолированный TU — единственный чистый способ. При `STOMPTALK_PARSER_AVX2 = 0` объект исключается из CMake — правильно.

**Файл `before/src/parser_impl.hpp` в snapshot** — только исторический baseline для диффа, не активный код.

## 4. Минимальные исправления и performance-эксперименты

### Минимальные исправления

1. **Задокументировать инвариант `avx2_state()` в `boundary`-проверке** (`parser_impl.hpp:239`): однострочный комментарий о том, что avx2_state() детерминирован и единственен.

2. **Добавить constexpr-проверку в `name_group`** (`name_group.hpp:116` после static_assert): вспомогательная `constexpr bool has_discriminator()` + static_assert или warning через `[[deprecated]]` trick.

3. **Тест на `is_header` с пустым view и пустым литералом** — проверить что assert срабатывает или поведение ожидаемо.

### Три конкретных performance-эксперимента

**Эксперимент 1: Изолировать is_content_length из хвоста Os/SSE2**  
Временно заменить `sse2::is_content_length` вызовом `scalar::is_content_length` (через `equal<13>`), перемерить только Os/SSE2. Если регрессия исчезает — проблема в `_mm_load_si128` с `content_length_sse2` (константа попадает в отдельную cache line). Если нет — причина в другом месте.

**Эксперимент 2: `perf annotate` на `hdrline_hdr_key` до/после**  
Запустить `perf record -e cycles:u -g` и `perf annotate` на `hdrline_hdr_key<3u>` в gcc16/Os/SSE2. Сравнить процент на `_mm_load_si128` (константа) vs процент на `_mm_loadu_si128` (данные). Это даст точечный ответ на гипотезу о cache miss без запуска полной перемерки.

**Эксперимент 3: Измерить с STOMPTALK_TRAMPOLINE=1 при -O2**  
STOMPTALK_TRAMPOLINE отключает inline tailcall. Если результат при O2+trampoline ближе к Os, это указывает что часть разницы — именно избыточное инлайнирование шаблонных instantiations, а не cache miss. Это поможет решить нужен ли PGO или просто `-foptimize-sibling-calls`.

## 5. Недостающие boundary/negative/corpus тесты

**Точные случаи:**

1. **`equal<N>` на граничных размерах каждого SIMD-уровня:**  
   - `equal<8>`, `equal<9>`, `equal<15>`, `equal<16>`, `equal<17>` (граница SWAR→SSE2)  
   - `equal<32>`, `equal<33>` (граница SSE2→AVX2)  
   - Случай "несовпадение ровно в последнем байте" для каждого размера  
   - Все тесты с guard page сразу за концом буфера

2. **`equal(data, text, size)` runtime:**  
   - `size=0, data=nullptr, text=nullptr` — должен вернуть true без UB  
   - `size=1, data=text` (один байт, одинаковый указатель)  
   - `size=14` (длина content-length) при несовпадении в каждой из 14 позиций

3. **`scan_header` с borrow-провокатором:**  
   Входная строка вида `\x01\x01\x01\x01\x01\x01\x01\x00:value` — байт 7 (NUL) после семи байт `0x01`. zero_mask(word) пометит все 8 байт (borrow propagates forward). Проверить что ctz возвращает позицию 7, не 0.

4. **`is_header` с пустым именем и строковым литералом `""`:**  
   `is_header<swar>{}({nullptr, 0}, "")` — граничный случай с assert.

5. **Parser: content-length=0, тело начинается с NUL:**  
   `SEND\ncontent-length:0\n\n\0` — NUL является терминатором фрейма, не телом. Проверить что `payload_size=0`, `STOMPTALK_FRAME_COMPLETE`.

6. **Parser: content-length близкий к max uint64:**  
   `content-length:18446744073709551615` — проверить ERROR_BODY_LIMIT, не переполнение `payload_offset + count`.

7. **AVX2 backend с размером входа 31, 32, 33 байта** (граница chunk):  
   Убедиться что переход AVX2→SSE2→scalar не теряет байт при хвосте.

8. **Fuzz с `max_len=16` и `max_len=33`** — принудительно исследовать граничные размеры SIMD, которые при `max_len=4096` встречаются редко.

## 6. Что пока не усложнять

**Не добавлять SWAR-equal.** Использование `memcmp` для остатка <16 байт — правильное решение. Для коротких строк STOMP (имена заголовков 4–20 байт) компилятор развёртывает `memcmp(data, text, N)` в несколько инструкций при compile-time N. Отдельный SWAR-equal добавил бы код и второй bitmask-путь без измеримого выигрыша. Контрпример в mask-counterexample.json прямо показывает, что zero_mask даёт ложные срабатывания — поэтому правило «не трогать» здесь обосновано.

**Не SIMD-accelerate `method_state`.** Команды STOMP (`SEND`, `MESSAGE`, `CONNECT`, `CONNECTED` и т.д.) имеют длину 4–9 байт; scalar цикл с `while (*p >= 'A' && *p <= 'Z')` работает ровно столько тактов, сколько символов. Методов в кадре один; заголовков — десятки. Перегонять метод через SSE2 даст погрешность в пределах шума.

**Не трогать `append`, `publish`, `finish_value`.** По профилю они занимают 10–12%, 8–10% и 5–9% соответственно — это реальный вес, но он связан с выделением памяти (stackbuf) и перемещением view-ов, а не с алгоритмическими неэффективностями. Улучшение потребовало бы изменения протокола хранения (arena, zero-copy), что далеко выходит за рамки backend-слоя.

**Не выключать AVX2 из-за регрессий в Os.** Os-сборки в production в большинстве серверных сценариев не используются; O2/O3 + производительный CPU — целевая конфигурация. Одиночные Os-регрессии не являются основанием для отключения backend по умолчанию.

## Сопоставление с evidence/REVIEW.md

**Согласуется полностью:**
- Архитектура сканер/equal
- memcmp для остатка (не SWAR equal)
- zero_mask только для присутствия, не для равенства
- Разделение packed/portable констант content-length
- Необходимость parser_avx2.cpp как target-контекста
- Отсутствие общего ускорения; шум в коротких сценариях (spread 28–76%)
- Удаление `_`-хелперов не являются упрощением алгоритма

**Добавляю от себя:**
- Конкретная гипотеза для Os/SSE2 регрессии (P1-A) и метод проверки
- Хрупкость `boundary`-проверки для AVX2 (P1-B)
- Отсутствие static_assert в `name_group` при отсутствии дискриминатора
- Граничные случаи `equal<0>` с nullptr
- Три конкретных эксперимента
- Восемь точных boundary-тест-кейсов

**AVX-Memmove reference** (`reference/avx-memmove/memcmp.c:1143`): идея каскадного выбора ширины (`< 8 → 8 bytes`, `< 16 → 16 bytes`, `< 32 → 32 bytes`) заимствована корректно. Типизированные dereference из reference (`*(uint32_t*)ptr`) не перенесены — используются `memcpy` для uint64 и `_mm_loadu` для SIMD. AVX-512, выравнивание входа и streaming stores из reference не нужны и не добавлены.

---

**Итог:** реализация архитектурно чистая и корректная. Производительность не улучшилась; регрессии в Os/SSE2 требуют объяснения перед изменением производственной конфигурации. Минимальный набор: один performance-эксперимент (изоляция is_content_length), документация инварианта AVX2 в boundary-проверке, граничные тесты equal<0>/scan_header/parser.
