## Полезное

Claude воспроизвёл общее замедление этапа 3 на O3 и проверил две небольшие

## Замечания к выводам

1. **Не принимать cold как универсальную оптимизацию.** Внешняя рекомендация
   «при неизвестном build type применить» не следует из таблицы: потеря O2
   около 5.2% больше выигрыша O3 около 2.6%. Слова, что потеря 3% меньше
   регрессии 2.2%, также арифметически неверны. Нужна матрица backend и сценариев.
2. **I-cache причина не подтверждена.** Размер функции и .text не доказывают
   cache misses. Cold меняет размер, размещение и вероятности ветвей сразу;
   noinline также меняет вызовы, пролог и распределение регистров. Для вывода
   о причине нужны более узкие эксперименты/счётчики. В гипотезах Claude 48K,
   12-way ошибочно названы L1I: `/sys/devices/system/cpu/cpu2/cache` показывает
   L1D 48K/12-way, L1I 32K/8-way. Шесть перечисленных сохранённых регистров
   ошибочно названы семью.
3. **Сводка Os неполна.** Лог `cold/logs/3way-Os.txt` содержит нормальные пары
   real/user 9.70/9.68 и 10.15/10.13, а не один валидный cold-замер. Третий
   9.94/86.76 имеет аномальный user. У baseline все три real: 9.64, 9.42,
   9.61; в отчёте оставлены только два. Равный размер кода сам по себе
   не доказывает равную скорость. Все исходные строки сохранены также в
   `external-timing-excerpts.json`, извлечённом из JSONL tool results.
4. **Аномальное user time не объясняется простым scheduler burst.** Для
   однопоточного процесса на одном CPU user в несколько раз больше real
   требует проверки измерителя/учёта; источник причины пока не установлен.
   Новая проверка использует монотонное время отдельного subprocess, без
   интерпретации этих повреждённых CPU-time значений.
5. **Оценка доли antoull арифметически неверна.** Утверждение, что 51 нс
   экономии на 10 кадров — меньше 0.01% всего времени, смешивает разные
   количества кадров. При ~690 нс на 10 кадров это ~7.4%, если допустить
   саму исходную оценку 51 нс. Она тоже не доказана для двух цифр purestomp.
6. **Патч не готов для всех компиляторов.** GNU `__attribute__((cold))`
   добавлен без условного макроса для поддерживаемых компиляторов.
   И сама характеристика «редкая функция» не следует из одного вызова на
   кадр: поток может состоять целиком из content-length кадров.

`cold` сообщает GCC о редком исполнении, включает оптимизацию на размер и
может менять размещение; пути к вызовам помечаются маловероятными. Это больше,
чем запрет inline. См. [GCC 15.3: cold](https://gcc.gnu.org/onlinedocs/gcc-15.3.0/gcc/Common-Function-Attributes.html#index-cold-function-attribute).

## Независимая проверка root

`verify.py` сверяет все исходники cold с собственным измеренным baseline:
различается только antoull.hpp. Затем собирает отдельную копию GCC Os/O2/O3,
проверяет CTest, Clang ASan/UBSan + CTest. Матрица purestomp: 10 млн кадров,
Scalar/SWAR/SSE2, прогрев + три чередующиеся пары. O3/SSE2 дополнительно
100 млн кадров, три пары. SEND с content-length отдельно проверяется на
whole/byte/chunk:7: прогрев + пять повторов, полезные счётчики совпадают.
Подготовка и проверки закончены до benchmark; backend задан явно.

Все собственные команды, stdout/stderr и значения — в `verification/run.json`.
Это исследование компромисса, не приёмка патча в основную библиотеку.

## Результат проверки

Purestomp, 10 млн кадров, Δ медианного времени cold к baseline:

| Flags | Scalar | SWAR | SSE2 |
| --- | ---: | ---: | ---: |
| Os | -3.63% | +5.55% | +3.07% |
| O2 | -6.77% | -0.30% | +3.66% |
| O3 | -1.20% | -3.89% | -2.07% |

O3/SSE2, 100 млн кадров, три пары: **6.836723 → 6.702501 с**,
**-1.96% времени**. Разброс 1.34% / 0.10%.

Размер .text совпал с внешними результатами: Os 22133, O2 27830, O3 30118 байт.
GCC CTest Os/O2/O3 и Clang ASan/UBSan CTest прошли. Счётчики полезной работы
во всех запусках совпали; source-копия отличается от baseline только antoull.hpp.
Дополнительный fuzz в этой проверке атрибута не запускался.

SEND whole O3: 37.41 → 35.70 нс (−4.58%), но разброс обоих вариантов около 5%,
поэтому уверенный выигрыш этого короткого сценария не заявляется. O3 byte
и chunk:7 имеют дельты +1.16% / +1.42%, сопоставимые с разбросом. SSE2/Os
и SSE2/O2 регрессируют в общем purestomp. SWAR/Os тоже регрессирует (+5.55%).
В SWAR/O2 −0.30% сопоставимы с шумом. Универсального улучшения нет.

**Решение:** патч cold не переносить в production как общее ускорение.
Полезное направление — отдельно проверить границу инлайна checked wrapper,
сохранив шаблонный antoull и быстрый путь частых коротких чисел. Это следующий
измеряемый эксперимент, пока без реализации и без обещания ускорения.
Размещение по cold не равно доказанному лечению I-cache.
