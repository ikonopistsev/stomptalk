## Согласованные ограничения

1. Законченное ядро C API, C++14 внутри; caller-owned preallocated memory,
   никаких malloc/realloc на горячем пути. Закрытые parser/stackbuf используются
   только через C-интерфейс. Не проектировать общий контейнер или allocator.
2. Сохранить маленькие состояния и дерево tailcall. Любая альтернатива требует
   существенного измеренного выигрыша либо явного упрощения. Удалять if только
   по инварианту, а не ради меньшего количества строк/переменных.
3. В v2 reserve учитывает borrowed и copied строки до принятия входа.
   Изменение внутреннего push с bool на void/assert намеренное: место уже проверено.
   В 1.8.0 отказ push сбрасывал указатель; оригинал не изменён. Не требуй вернуть
   старое поведение в закрытом v2 только ради совместимости несуществующего API.
   Проверь, действительно ли callers обеспечивают новый контракт во всех случаях.
4. Внешние данные могут быть невалидными: syntax, escape, limits и overflow —
   реальные ошибки, runtime-проверки обязательны. Внутренние гарантии — assert.
   Для name classifiers ненулевой size требует валидную память, NULL/0 допустим.
5. Метаданные целые, payload выдаётся фрагментами и не копируется/не хранится
   parser. Сохраняются BEGIN/COMPLETE, consumed, OUTPUT_FULL/NEED_INPUT,
   приоритеты/offsets ошибок, sticky error, порядок/дубликаты headers, lifetime.
6. LF/CRLF, escaping, unknown names, полный диапазон uint64 content-length
   и ведущие нули сохраняются. Ядро распознаёт только content-length;
   классификатор всех headers — отдельная необязательная клиентская функция.
   Исходное length-dispatched шаблонное antoull сохраняется.
7. Один hdrline scanner, каскад AVX2 → SSE2 → SWAR8 → bytes. Без чтения за
   доступный диапазон. equal<N> — compile-time выбор, короткое сравнение memcmp.
   Known-length body пропускается по длине, unknown-length ищется memchr.
   CPU/OS/build gate при init, AUTO=SSE2/SWAR, AVX2 opt-in. Не вводить ISA dispatch
   на каждом header и глобальное требование AVX2. Отдельный AVX2 TU нужен для ISA.
8. Одна aligned константа "\ncontent-length:" (16 байт + C terminator).
   Целый wire проверяется по 16 байтам, fragmented name — constant+1, длина 14.
   Полный key в начале нового input не гарантирует доступность предыдущего LF.

## Что проверить в первую очередь

- Все переходы учёта byte_left: reserve → own/own_metadata/own_token →
  finish_token → publish → recycle. В том числе заимствованный полный кадр,
  следующий кадр после скопированного, OUTPUT_FULL до первого байта нового
  токена, BYTE_LIMIT с уже готовыми кадрами, пустой остаток retain, escape,
  пустые значения и куски с единственным backslash. Дай доказательство/контрпример.
- Каждый снятый runtime-тест: не скрывает ли он реальную сетевую ошибку или UB?
  memcpy/memmove при нулевой длине, доступные pointers, subtract/shift и overflow.
  tailcall вызывается только при OK? append(decoded byte) всегда уже owned?
  finish_token может ли получить size=0 и data!=NULL на успешном пути?
- Видимость helpers в AVX2 и baseline TU, inline/outline, параметры и повторные
  загрузки полей, связанные записи и копирование. Где осталась избыточная работа?
  Различай compile-time if и реальные branches; не делай вывод по одному C++ if.
- Проверенные просадки: Clang O3 h0_lf +7.89%, fragment_chunk_63 +3.20%,
  send_length_byte +2.21%; GCC O2 send_length_chunk_7 +2.75% времени.
  Уточни возможные причины по коду/asm, отделяя гипотезу от установленных фактов.
- PGO O2 escaping +26.83% против нового plain (spread 2.24/1.96%);
  O3 escaping +2.32%. Обучение unit suite + 5 млн purestomp кадров; основной
  workload входил в training, серверный эффект неизвестен. Не смешивать дельты
  before→after, plain→PGO и старого split→hdrline.
- GCC O2/O3 .text вырос при снижении instructions/branches; Clang уменьшился.
  Top-5 — self внутри новых границ функций после inline. Доли не доказывают
  причинность, снижение branches не доказывает устранения branch misses.
- Дополнительные простые оптимизации в оставшихся горячих функциях. Не повторяй
  уже выполненное как новую рекомендацию. Предпочти максимум три независимых
  локальных изменения без новых persistent flags, дерева специальных случаев
  или собственного replacement для libc без измерений.

## Формат ответа

1. Вердикт отдельно: корректность, простота, скорость; принять/уточнить/отклонить.
2. Таблица существенных правок: файл:строка, логическое обоснование,

   непроверенная гипотеза. Точный путь, строки, input либо доказательство.
4. Не более трёх следующих оптимизаций: минимальный diff или псевдокод,
   влияние на простоту, ожидаемый механизм выигрыша без выдуманных процентов,
   риск, конкретная A/B матрица и критерий отклонения. Можно рекомендовать
   остановиться, если дальнейшее усложнение не оправдано.
5. Реальные пробелы тестов, оценка benchmark/PGO и ограничений вывода.

## Уточнение после замечания пользователя про equal(size=0)

Snapshot обновлён дополнительно к первоначальным упрощениям. Рассмотри изменения
src/backend/swar.hpp и src/is_header.hpp: raw equal теперь вызывает memcmp
непосредственно, с assert ненулевых указателей. Nullable пустые views обработаны
на уровне is_header. Нулевой размер остаётся нормальным терминальным хвостом
SIMD (например, equal<16> → equal<0>); memcmp с валидными указателями его принимает.

Пользователь хочет видеть обычное сравнение главным действием и убрать проверки,
не требуемые реальными callers. Проверь, стало ли разделение ответственности
понятнее; не перепутай нулевую длину с NULL-указателем. Достаточно ли малого
изменения, или можно выразить тот же контракт проще? Не вводить дополнительные
флаги или шаблонные классы ради одного терминального случая.

Дополнительные данные: evidence/equality/README.md, checks.json и changes.patch.
Все шесть GCC/Clang Os/O2/O3 .text/.rodata parser+consumer побайтно прежние;
новый PGO тоже совпал. Поэтому ускорение полного parser этой правке не приписано.
Проверь отдельно потенциальную стоимость runtime equal на точных кратных 16/32:
теперь конечный memcmp(...,0) возможен. В библиотечном hot path runtime is_header
не используется; не переносить вывод о библиотеке на произвольного C++ клиента.
Микробенч этого client helper ещё не проводился. Существующие nullable/zero,
SIMD-tail/guard-page тесты прошли Debug, Release и ASan/UBSan.
