# Сверка завершённого Claude review

Исходное [независимое ревью](../../pgo-matrix/2026-10-28/review/claude-20261028T073809446931Z/review.md)
сохранено без правок. Явных ошибок корректности ревью не предъявило; это не
доказательство отсутствия ошибок. Ниже сверка с кодом и фактическими запусками.

- Проверка `status_ == OK` в `tailcall` выглядит инвариантом при текущих callers.
  Замена на assert — кандидат для отдельного A/B. В серверный кандидат она не
  включена: пользователь попросил убрать неиспользуемые методы, а эффект этой
  правки пока не измерен.
- Двойной `get_layout` при init подтверждён. Это холодный путь, не причина
  стоимости каждого заголовка. Оставлен для отдельной небольшой правки.
- Условие доступности `LF + content-length + ':'` подтверждено; чтения до начала
  входного диапазона нет. 14-байтный fallback использует смещение в той же константе.
- `own()` опирается на уже документированное требование непересекающейся памяти
  parser/input (`include/stomptalk/parser.h`, README). Это не новое молчаливое
  предположение, как написано в ревью.
- Утверждение о непроверенном fuzz-пути hdrline неверно: в
  [run.json](../../header-line-study/2026-10-28/runs/20261028T062508203190Z/run.json)
  sanitizer/fuzz конфигурация содержит `STOMPTALK_EXPERIMENT_HEADER_LINE=ON`.
  Финальный ручной прогон: 250275 запусков / 16 с; предыдущий: 420414 / 31 с.
  После удаления старой цепочки отдельный флаг больше не нужен.
- Предложенные проверки пустого значения и content-length на границе уже есть:
  `unit_v2.cpp`: `empty-value`, `length`, `binary-leading-nul`, `variants` с каждым
  разрезом, chunk=1 и chunk=7. Они покрывают LF в предыдущем входном буфере и
  побайтовую подачу. Проверка корректности не заменяет измерения byte-сценария.
- Value-only сканирование длинного значения имеет смысл проверить отдельно.
  Предложенный возврат к `separator+1` повторно сканирует часть уже загруженного
  блока. Если делать опыт, сначала использовать его оставшуюся маску, затем
  перейти к следующему блоку. Причина длинного сценария пока не установлена.
- Матрица PGO уже полностью собрана с hdrline=ON. Изменение default само по себе
  не даёт нового сравнения. Для проверки влияния PGO на выбор цепочки нужны
  отдельные split+PGO / hdrline+PGO. В ревью смешаны дельты разных экспериментов:
  +33.71% относится к GCC O2 line-vs-split, +7.95% — GCC O3 PGO-vs-plain на line.
- Утверждение, что сервер обязательно получит меньший выигрыш, не проверено.
  Синтетический purestomp входил в обучение; рост `.text` и локальные просадки
  сохраняются как ограничения. Направление и величину эффекта даст серверный A/B.

Решение для передачи: оставить одну проверенную цепочку hdrline, удалить
прежние состояния/сканеры и пустой макрос target, сохранить каскад backend-ов.
Новых оптимизационных гипотез в parser не добавлять. PGO остаётся отдельной
опцией сборки. Критерии последующих ревью — упрощение и ускорение всего parser,
затем влияние на сервер; оба результата требуют раздельного подтверждения.
