# Первая реализация stomptalk v2 — 27 октября 2026

Ветка `stomptalk-smid`, исходная 1.8.0: `54a926c34c4fa6274357d2683920125a5bbfb1b3`. Код не закоммичен. Неизменённые исходники старой версии находятся в [legacy](legacy/). Все сравнения проверяют полезные счётчики; неверный backup с нулевыми method/header ID в сравнения не включён.

## Реализованный контракт

- C99 API, C++14 внутри. Один выровненный блок владельца, без malloc/realloc/free в ядре, включая init. Устанавливаются только четыре C-заголовка; старый callback API несовместим с v2.
- Упорядоченные `frames[i]`, `headers[j]`, уже разобранные method ID/content-length, BEGIN/COMPLETE и payload offset. Метод и заголовки целые; payload выдаётся частями, не сохраняется. COMPLETE требует проверенного NUL.
- Defaults: 64 записи, 256 пар, 32768 байтов строк, 64 заголовка на кадр; отдельный max_body_size. В лимите строк учитываются метод и все декодированные ключи/значения, включая временно заимствованные.
- Дерево состояний и tailcall основаны на `123/backup/parser.cpp`. В debug и настроенных sanitizer-сборках переход возвращается во внешний run. Лимит stackbuf проверяется до записи для возобновляемого OUTPUT_FULL; намеренный сброс его курсора при failed push сохранён.
- Scalar, SWAR 8 байт, SSE2 16 байт; безопасные хвосты и CPU/OS/build-проверка при init. AUTO выбирает доступный SSE2, иначе scalar. AVX2 зарезервирован, но не реализован.
- FNV исключён из ядра. Полный классификатор заголовков вызывается только клиентом. Имена сгруппированы по длине; размер выводится из constexpr-литерала, сравнение использует memeq<N>/constant memcmp. sv и общий класс словаря отложены по последнему решению пользователя.
- STOMP 1.2: LF/CRLF, строгий межкадровый NUL, literal CONNECT/CONNECTED, escaping остальных методов, сохранение дубликатов и первого content-length (включая ноль), бинарный payload. UTF-8 байты проходят без полной проверки кодировки; неизвестный метод из A–Z выдаётся с UNKNOWN и строкой.

## Проверенные изменения по этапам

1. [names-before](names-before/) / [names-after](names-after/): размеры литералов вместо ручных чисел. GCC O3: размеры горячих функций парсера совпали, helper detect_header стал на 8 байтов меньше. Пять парных проб показали около 0,1–0,5% разницы: ускорение не заявлено.
2. [perf](perf/): первая полная матрица. SWAR с повторным просмотром восьмёрки оказался медленнее scalar в O2/O3; это не было принято как выигрыш SWAR.
3. [swar-first-bit](swar-first-bit/): на little-endian первая установленная позиция маски точна, несмотря на возможные ложные последующие биты от borrow. Удалён повторный проход по слову. На полном purestomp SWAR быстрее предыдущего SWAR на 19–25%, затем быстрее scalar во всех трёх режимах. Для другого порядка байтов остаётся скалярное уточнение.
4. [return-paths](return-paths/): убраны повторный own_metadata перед own_token и повторные обходы уже сохранённых метаданных после BEGIN; пустое тело без длины сразу идёт к frame_end. Новых состояний/флагов не добавлено. Это упростило владение и улучшило несколько коротких сценариев, но на общем O3 purestomp SSE2 результат практически не изменился; scalar O3 в этой паре стал примерно на 2% медленнее. Ни общей победы этой правки, ни полного устранения всех просадок не заявляем.

## Накопитель и объём копирования

[Первый микротест](stackbuf/) выявил сильную зависимость от контекста инлайнинга: в одном варианте constant 64-byte memcpy GCC превратил в rep movsl, в другом — в векторные stores. [Контрольный вариант](stackbuf-controlled/) сохраняет обе измеряемые петли noinline и дополнительно скрывает длину диапазона от constant folding. Это диагностические тесты накопителя, а не приёмка парсера.

| O3, 64 байта за запись | Старый, нс | Новый, нс |
| --- | ---: | ---: |
| byte | 26.786 | 19.081 |
| range64 | 0.938 | 0.498 |
| range-runtime | 1.331 | 1.106 |
| fragments7 | 4.535 | 6.378 |

На runtime-диапазоне просадки нет; на серии фиксированных семибайтовых добавлений в O3 новая настраиваемая версия медленнее. Поэтому универсальное «stackbuf не замедлился» не утверждается. Менять memcpy или добавлять внешнюю библиотеку по одному микротесту не стали.

[Счётчики копирования](copy-counts/copies.csv) получены в отдельных инструментированных снимках; их времена не используются. Считаются записи строковых байтов и явное уплотнение, без записей самих результатов/описателей. Например, whole SEND с длиной: 19→0 строковых байтов; тот же ввод по байту: 19→19; escapes: 14→14. В примере complete + начало следующего payload: 30 байтов строк, затем 22 байта carry и 32 байта одного header descriptor при следующем вызове. Растущий префикс на каждом байте заново не копируется. Payload ядро не сохраняет.

## Корректность и воспроизведение

Финальные логи: [validation-complete](validation-complete/). Каждый полный запуск: **8292 потоковых варианта, 737857 проверок**. GCC O0/Os/O2/O3, Clang O3, ASan/UBSan, static/shared CMake, установка и отдельная C99-компиляция/линковка прошли. Сюда входят все разрывы небольших кадров, byte/chunk:7, отравление входов, guard pages, все значения байта для SWAR, 63/64/65 заголовков, лимиты и OUTPUT_FULL, ошибки/reset, бинарные NUL, leading-zero uint64, 100000 кадров за вызов и round-trip всех ID.
Последний ручной fuzz: **80580 запусков / 31 с**, seed 1803, ASan/UBSan, max_len 8192, RSS limit 512 MiB, без находок. Сохранены seed archive, команда, hash бинарника и лог. Суммарно по четырём состояниям кода: 356513 запусков; это не число проверок одной финальной сборки. Расписание и серверный fuzz не создавались.
Undefined symbols финальной shared-библиотеки не содержат allocator: есть C++ personality и libc memchr/memcmp/memcpy/memmove. Heap allocation в тестовых потребителях относится к ним, не к ядру.

Команды из корня stomptalk (для нового performance-прогона выбирайте новый --out):

```sh
python3 artifacts/parser-v2-implementation/validate.py /tmp/stomptalk-validation
python3 artifacts/parser-v2-implementation/run_stage.py --out /tmp/stomptalk-perf-new
```

Точные команды каждого сохранённого этапа находятся в его run.json/checks.json; исходники в snapshot. Контрольный run_stage сейчас возьмёт текущий код, а первоначальный perf/snapshot сохраняет первый вариант. Прошлые результаты и неудачный служебный запуск до исправления executable-mode при копировании бинарника сохранены, не подменены.

## Решение ревью

Первая реализация пригодна для следующего цикла интеграции и оптимизации. Упрощение: нет callback/hooks/FNV в пути, нет владения чужими входными буферами, нет body accumulator, один C-контракт и один внешний блок. Цена: больше описателей/проверок на вызов, перенос активных метаданных и три скомпилированных backend. Ускорение полного purestomp и полезность SWAR/SSE2 подтверждены отдельно; низкая задержка всех коротких/фрагментированных случаев ещё не достигнута. AVX2, custom memmove, SV-класс словаря и изменения RPC/SWIG интеграции отложены. Другие архитектуры/компиляторы, PGO/LTO и перемешанный реальный RPC-корпус требуют отдельной проверки.
