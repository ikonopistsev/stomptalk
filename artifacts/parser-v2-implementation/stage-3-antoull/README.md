# Этап 3 — возврат antoull и внутренние предусловия

Ветка `stomptalk-smid`, 2026-10-27. Корректность проверена. Как ускорение всего
парсера этап не принят: общий Release/AUTO замедлился на **2.53%**.
Возврат шаблонного antoull сохранён по запросу пользователя; быстрый конвертер
сам по себе не гарантирует быстрый парсер. История этапов — [PERFORMANCE.md](../../../PERFORMANCE.md).

## Изменения и упрощение

- В `include/stomptalk/antoull.hpp` восстановлен шаблонный конвертер 1.8.0:
  switch по известной длине → `antout<int64_t, N>::conv`. Шаги 1..18 разрядов
  разворачиваются, цифры проверяются. При runtime-длине switch остаётся;
  при константной длине компилятор может выбрать специализацию заранее.
- Новый checked overload сохраняет полный диапазон `uint64_t`, принимаемый v2.
  Для 19/20 цифр проверяются префикс и последние 18 цифр; переполнение, пустое
  значение и неверные символы отвергаются. Лишние ведущие нули допустимы;
  output не меняется при ошибке. `finish_value` вызывает этот overload.
  Архивный `_antoull.hpp` не изменён. Старая замена шаблона циклом не имела
  отдельного измерения, доказывающего преимущество конвертера.
- Внутренние `is_header`, `is_content_length`, `detect_method`, `detect_header`
  заменяют runtime-null проверки на `assert(data || !size)`. Публичный C API
  продолжает проверять параметры. [Аудит проверок](assert-audit.md) объясняет,
  почему проверки wire data, памяти, overflow и public execute оставлены.
- Новых состояний, heap, registry или callbacks нет. Накопитель, safe tails,
  escaping, streaming payload и хвостовые переходы не менялись.

Упрощение ограничено: вернулся знакомый шаблонный алгоритм и убраны дублирующие
внутренние ветви. Поддержка 19/20 цифр нужна для сохранения уже выбранного
контракта v2; это дополнительный код относительно исходных 18 цифр.

## Проверки

GCC O0/Os/O2/O3, Clang O3, ASan/UBSan: **8292 потоковых варианта,
1 763 680 проверок** в каждой сборке. Shared/install и C99 client прошли.
Добавлены границы uint64, 10 000 детерминированных случайных чисел,
ведущие нули, недопустимые байты на каждой позиции и guard-page числа.
Из ревью Claude добавлен прямой SSE2-vs-scalar scanner тест.

[Логи сборок и проверок](validation/checks.json), [ручной fuzz](validation/fuzz.json):
seed 1806, **336 034 запуска / 21 с**, без находок; ASan/UBSan, LSan отключён
из-за среды. Расписание не создавалось. [Финальная сверка](final-checks.json)
подтверждает hash снимка и воспроизводимость пяти generated файлов.

[Полный разброс и разделение вкладов](scenarios.csv). В `send_length`
просадка появляется уже с конвертером (+8.22%), после замены проверок — ещё

конкретной аппаратной причины. Для этого случая отдельно сохранены
[три профиля и команды](send-length-profiles.json), `send-length-*-report.stdout`
и `send-length-*-annotate.stdout` с инструкциями `finish_value`.
В отдельном 200-миллионном прогоне собственная доля `finish_value` выросла
с 5.42% до 10.50% (только antoull) и 12.16% (итог); потерь samples нет.
Это выделяет функцию для следующей оптимизации, но не устанавливает причину
на уровне I-cache/предсказателя переходов.
В листинге есть конкретное изменение интеграции: `finish_value` сохранял два
callee-saved регистра и резервировал 8 байт стека, теперь сохраняет шесть и
резервирует 88 байт. Этот пролог исполняется и для обычных headers. Следующий
узкий эксперимент — граница inline между развёрнутым конвертером и этой
общей функцией; сам шаблонный алгоритм для него менять не требуется.

Путь `body64k_nul` вообще не использует antoull; его уменьшение времени нельзя
приписывать ускорению преобразования числа. Наблюдения сохранены полностью,
но причина этой дельты не установлена.

## Изолированный конвертер

[Микротест](number-bench.cpp), [runner](measure-numbers.py),
[45 ячеек](numbers.csv), [все повторы и команды](numbers/run.json).
Прежний checked loop сравнивается с checked antoull, checksum и число
успешных преобразований проверяются. Для каждого случая 256 разных чисел,
5 млн преобразований, прогрев и три пары. Измеряются runtime-длина и длина,
переданная как константа шаблонному измерителю. Это отдельный контекст inline
и оптимизации; он не подменяет parser benchmark.

O3, константная длина, нс/преобразование:

| Цифр | Прежний цикл | antoull |
| --- | ---: | ---: |
| 1 | 0.441 | 1.287 |
| 3 | 6.400 | 1.599 |
| 6 | 12.638 | 2.347 |
| 12 | 25.426 | 3.820 |
| 18 | 37.929 | 6.056 |
| 20 | 41.885 | 6.905 |

В варианте, ближе к вызову из парсера, длина читается во время выполнения:
6 цифр — 12.659 → 2.580 нс, 18 цифр — 38.126 → 5.999 нс. Сам текст числа
известным компилятору не является в обоих вариантах.

Преимущество шаблонного преобразования подтверждено для этих многоразрядных
примеров относительно прежнего цикла. Для одной цифры результат обратный.
Сравнения со всеми существующими алгоритмами здесь нет, утверждения
«самый быстрый вообще» этот тест не делает. Время включает решения компилятора
об inline/разворачивании в конкретном harness.

## Ревью и расширение списков

Claude завершил внешний запуск. [Проверка его замечаний](../../parser-v2-review/2026-10-27/review-round-4/root-triage.md)
отделяет полезный SSE2 test gap от неподтверждённых причин просадки и предложений

[Оценка C++ расширения](header-extension.md) и [compile/run probe](header-extension.cpp)
подтверждают: конкатенация типов и отдельный функтор работают в C++14, GCC и

это учтено. Никакого framework в production-код не добавлено.

## Ограничения и решение

Корректность и требуемый возврат antoull выполнены. Числовой микротест полезен,
но общего ускорения Release/AUTO нет. Перед принятием этапа как оптимизации
нужно устранить просадку короткого SEND/общего purestomp и проверить контекст
inline/расположение выросшего конвертера, сохраняя простоту и numeric contract.
Дополнительные экспериментальные варианты в библиотеку сейчас не внесены.

Прежние вопросы TCO при GCC O1/Og, формального C++14 lifetime, оставшегося
форматирования ядра и непроверенных архитектур этим этапом не закрыты.
AVX2-сканер парсера по-прежнему отсутствует; три backend в матрице —
Scalar/SWAR/SSE2. C++ extension остаётся отдельной оценкой, C API не расширен.
