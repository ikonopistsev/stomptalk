# Исполняемые переходы и инструкции — 28.10.2026

Контроль по вопросу пользователя: стало ли меньше переходов после объединения
header key/value. Один и тот же исходник из PGO-снимка, SSE2, O3, CPU 4 (P).
Варианты: split, hdrline без PGO, hdrline с PGO. Для split отдельно пересобраны
GCC/Clang O3, CTest/C99 прошли. Остальные binaries взяты из завершённой PGO-серии.

Один прогрев, три повтора по 10 млн кадров, порядок вариантов вращается.
`perf stat`: cycles:u, instructions:u, branches:u, branch-misses:u. Взяты
cpu_core-счётчики; cpu_atom не считает на выбранном P-ядре. Running=100% для
всех счётчиков, multiplexing нет. Медианы на один законченный кадр. Счётчики
охватывают весь probe/consumer и запуск процесса, не изолированную функцию.

## Вывод из счётчиков

- gcc16: split → hdrline без PGO: переходов -5.35%, инструкций -8.07%. С PGO относительно split: переходов -23.54%, инструкций -22.27%.
- clang23: split → hdrline без PGO: переходов -4.06%, инструкций -8.59%. С PGO относительно split: переходов -19.12%, инструкций -25.07%.

На этом корпусе тезис подтверждён: объединение уменьшает исполненную работу
у обоих компиляторов даже без PGO. Это не доказательство меньшего числа ветвей
для любого входа: long/fragmented сценарии раньше показывали регрессии.
Промахов предсказателя здесь очень мало; корпус повторяется и хорошо предсказуем.
Выигрыш нельзя свести только к устранению mispredicts.

## Как читать perf top

GCC/O3 plain: hdrline 37.83%, append 11.36%, start_state 10.27%. С PGO:
hdrline 45.65%, start_state 18.88%, done 8.63%. Рост доли hdrline происходит
при снижении общего времени; процент сам по себе не показывает замедление.
GCC finish_value меняет форму: hot body 11376 → 577 байт, появляется cold clone
1630 байт. По листингу часть append встроена в hdrline.

Clang/O3 PGO: 89.17% self попали в hdrline_done. Его символ вырос с 373 до
12173 байт; листинг показывает объединение большого количества работы в этом
состоянии. Отдельные helper-функции больше не являются хорошими единицами
сопоставления self-процентов до/после. Это соответствует большому росту .text,
уже указанному в основном отчёте.

## Размер исходников и оценка простоты

Активные src/include: 23 файла, 2726 → 2912 строк относительно снимка до
header-line. Сейчас одновременно сохранены обе цепочки и оба scanner для A/B;
поэтому полный объём дерева вырос. Число строк не измеряет сложность активной
цепочки. В новой цепочке key/value обрабатывает одно состояние hdrline вместо двух,
нет новых полей parser/кэша масок; backend и единая wire-константа прозрачнее.
PGO не меняет исходник. GCC/O3 .text 57653 → 55824 байт; Clang/O3 45188 → 79786.
Это размер всего probe с библиотекой и consumer, не только parser.

Файлы: run.json (команды), counters.json (все счётчики/повторы), *.csv (raw perf),
*-symbols.txt и *-hdrline.asm (nm/objdump). Дополнение получено после подготовки
замороженного Claude-review; существующий review snapshot не переписывался.
