Контекст и принятые пользователем решения:
- Законченное самостоятельное ядро C API, без зависимости от внешней SIMD lib.
- Сохранять стиль маленьких состояний и хвостовых переходов исходного parser;
  не переписывать всё в один огромный while без измеримого обоснования.
- Caller-owned память и монотонный stackbuf без realloc. У stackbuf push при
  нехватке места сбрасывает offset; уменьшение offset — сигнал отказа. Это дизайн.
- Escaping, CRLF/LF и частичный payload сохраняются. Payload не копируется и не
  хранится parser между вызовами; результат содержит фрагменты и completion flags.
- Scanner: обычные inline-функции 32/16/8/byte. equal<N> выбирается на этапе
  компиляции; хвост <16 — один memcmp. Слово SWAR относится к scanner, а не к
  особому алгоритму equality. Не требовать собственного SWAR memcmp ради имени.
- CPU/OS/build gate при init; AVX2 opt-in, AUTO=SSE2. Сам is_content_length не
  опрашивает CPU каждый раз. Единственная wire-константа "\ncontent-length:"
  содержит 16 байт плюс NUL: SSE2/portable raw сравнивают 16; накопленный key
  сравнивается memcmp(name, constant+1, 14). Без чтения за границей входа.
- Допускаются assert для ошибок вызывающего кода и внутренних предусловий.
  Для name classifiers size>0 требует валидную память; NULL/0 допустим.
  Удаление обработки NULL/4 как UNKNOWN — согласованное изменение контракта,
  а не случайная потеря обработки ошибки. Ошибки протокола и лимитов проверять.
- Fallback после switch: default:; затем общий return, как пользователь показал
  для method_name. Это закреплено в генераторе для name helpers.

Приоритеты ревью:
1. Каждую правку оценить отдельно по простоте и по скорости полного parser.
2. Найти проверки ради проверок: известный из контекста факт, повторное
   вычисление, ненужный helper/аргумент, runtime-ветка вместо инварианта.
   Отличать видимый if, исчезающий при компиляции, от реальной инструкции.
3. Особо рассмотреть выбор 14/16 байт в parser_states и nullable wire в
   is_header.hpp. Parser уже знает, что token borrowed/owned, но finish_token
   сбрасывает флаг. Можно ли выбирать сравнение в естественных ветках раньше,
   без новых постоянных флагов и дублирования дерева? Целый key в начале
   нового input не гарантирует доступность предыдущего LF.
4. Проверить объединённый hdrline + scan_header_line: разделитель и EOL в одном
   блоке, остановка на escape/invalid colon, literal CONNECT/CONNECTED, точная
   SWAR zero-mask после удаления первого colon, переходы 32→16→8→byte, разрывы
   LF/name/colon/value/CRLF, границы накопителя. Отличать borrow-based first-match
   mask старого scanner от точной новой маски.
5. Достаточность test suite и guard pages; предлагать только реально отсутствующие
   тесты, проверив имеющиеся. Нужен конкретный input/chunk schedule/ожидаемый ответ.
6. Проанализировать замеры и PGO: источник профиля, соответствие code/flags,
   held-out fixtures, profile-use diagnostics, benchmark consumer, CPU affinity,
   выбросы, code size, топ-5. Purestomp участвовал в обучении; это не server perf.
