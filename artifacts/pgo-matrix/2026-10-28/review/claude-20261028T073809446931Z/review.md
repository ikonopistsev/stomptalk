# Независимое ревью stomptalk smid-2 — 28.10.2026

## 1. Вердикт по трём осям

**Корректность: подтверждена с одной рабочей гипотезой.**
Явных ошибок не обнаружено. Арифметика wire-указателя безопасна; tailcall-guard корректно предотвращает вызов состояния с `curr == end`; `body_read` при точном совпадении длины не обращается за границу входа. Единственный нетривиальный вопрос — `own()` использует вычитание `uintptr_t` для проверки принадлежности диапазону: предполагается, что адрес входного буфера никогда не лежит случайно в пределах `byte_capacity` от начала внутреннего `bytes_`. В нормальной работе верно; документируется как молчаливое предположение, а не как ошибка.

**Простота: хорошая, с двумя уточнениями.**
Объединённый `hdrline` добавляет состояние при выключенном флаге, но не усложняет существующую цепочку. `stomptalk_parser_init` вычисляет layout дважды (строки 75–80 `stomptalk.cpp`) — это доказанное дублирование, хотя и вне горячего пути.

**Производительность: PGO даёт реальный выигрыш, но с зафиксированными регрессиями.**
Агрегированный тест (purestomp corpus): +17–39% млн/с в зависимости от компилятора и уровня оптимизации. Это не производительность сервера: corpus участвовал в обучении, поэтому оценка оптимистична для этого workload-а. Три held-out регрессии (ниже) реальны и не шум.

### P1-A — `tailcall`: статусная проверка инвариантно выполнима

**Файл:** `include/stomptalk/parser.hpp:47`
```cpp
if (p < end && status_ == STOMPTALK_PARSE_OK)
    return (this->*next)(p, end);
```

**Доказательство.** Просмотр всех мест вызова `tailcall` в `parser_states.hpp` показывает: `tailcall` вызывается только из ветки, в которой:
- не было `fail()` (который выставляет `PARSE_ERROR` и возвращает через `return fail(...)`);
- не было отказа `reserve()` / `finish_value()` (возвращают `return stop_` или `return false` с дальнейшим `return stop_`);
- не было `OUTPUT_FULL` (возвращает `return curr` напрямую).

Таким образом `status_ == STOMPTALK_PARSE_OK` в момент вызова `tailcall` — инвариант. Проверка присутствует в горячем пути (по профилю до 38–45% времени в `hdrline`), добавляет чтение поля из памяти при каждом переходе между состояниями.

**Рекомендация:** заменить на `assert(status_ == STOMPTALK_PARSE_OK)`. Если инвариант окажется нарушен (например, при будущем рефакторинге), assert в debug-сборке немедленно поймает это. В release с NDEBUG строка исчезает полностью.

**Статус:** избыточная работа, подтверждена статически. Эффект на скорость — гипотеза; требует A/B.

### P1-B — double `get_layout` в `stomptalk_parser_init`

**Файл:** `src/stomptalk.cpp:75–80`
```cpp
const auto error = stomptalk_parser_get_memory_requirements(&c, &r);  // вызывает get_layout
if (error) return error;
...
layout l{};
get_layout(c, l);  // повторно, результат уже известен
```

**Доказательство.** `stomptalk_parser_get_memory_requirements` внутри вызывает `get_layout` и возвращает только `l.total`. При успехе `init` вычисляет `l.frames`, `l.headers`, `l.bytes` заново, игнорируя возвращаемое значение второго вызова (оно заведомо `NONE` после первой проверки).

**Рекомендация:** вынести единственный `layout l{}; get_layout(c, l)` из `get_memory_requirements` в отдельный call-site, передавать `l` в `init` через параметр или вычислять один раз. Это init-only путь, на производительность парсинга не влияет.

**Статус:** подтверждённое дублирование кода.

### P2-A — `scan_header_line`: dead `key=false` per-block после нахождения разделителя

**Файлы:** `src/backend/swar.hpp:151`, `src/backend/sse2.hpp:100`, `src/backend/avx2.hpp:94`

Паттерн во всех трёх backend-ах одинаков:
```cpp
if (key && colons && ...)   // всегда false после первого нахождения separator
{
    separator = ...;
    key = false;
    colons &= colons - 1;
}
if (!literal)
    stops |= colons;
```

После установки `key = false` в итерации `k`, все последующие итерации входят в блок `if (key && ...)` и немедленно выходят. Компилятор видит изменяемую переменную `key` (не compile-time константу) и может не устранить ветку. В сценариях с длинными значениями (long_1024, 1024-байтная строка) это выполняется для каждого 8/16/32-байтного блока значения.

Это _гипотетическая_ причина регрессии `long_1024` (GCC/O3: +7.95%; GCC/O2 header-line series: +33.71%), но не доказанная причинная связь.

**Рекомендация:** A/B (см. раздел 4). Не менять без измерения.

### P2-B — `hdrline` wire-condition: правильность при `key_.size > 0`

**Файл:** `src/parser_states.hpp:101–102`
```cpp
detail::is_content_length<B>(key_,
    curr > begin_ && line.separator - curr == static_cast<ptrdiff_t>(key_.size)
        ? curr - 1 : nullptr);
```

`line.separator - curr` имеет тип `ptrdiff_t` (знаковый). Поскольку `scan_header_line` возвращает `separator` из диапазона `[p, p+block)`, а `p >= curr` на момент вызова, выражение неотрицательно. `key_.size` — беззнаковое; сравнение корректно благодаря неотрицательности.

Важнее: проверка выполняется до обновления `curr = line.separator + 1`, т.е. `curr` остаётся указателем на начало текущего чистого сегмента. Если ключ пришёл полностью в этом сегменте, `line.separator - curr == key_.size`; иначе (часть пришла в предыдущем вызове) разность будет меньше и мы падаем на 14-байтный путь.

**Статус:** логика правильная. Это не замечание, а подтверждение корректности.

### P2-C — `hdrline` experiment не охвачен fuzzer-ом в сборке по умолчанию

**Файл:** `fuzz/fuzz_v2.cpp`

Поскольку флаг — compile-time `#if`, для тестирования `hdrline` нужна отдельная сборка с `-DSTOMPTALK_EXPERIMENT_HEADER_LINE=ON`. Корпус fuzz-тестирует только путь `hdrline_hdr_key / hdrline_val`.

**Статус:** не ошибка, но пробел покрытия.

## 4. Три A/B-эксперимента

### Эксперимент 1 — `assert` вместо `status_ == STOMPTALK_PARSE_OK` в `tailcall`

**Изменение.** В `parser.hpp:47`:
```cpp
// было:
if (p < end && status_ == STOMPTALK_PARSE_OK)
// стать:
assert(status_ == STOMPTALK_PARSE_OK);
if (p < end)
```

**Ожидаемый выигрыш.** Устранение чтения `status_` из памяти и сравнения на каждом переходе между состояниями. Насколько это заметно — зависит от того, держит ли компилятор `status_` в регистре через inlining. Для Clang/O3/PGO, где `hdrline_done` содержит 90% семплов, это может быть нечувствительно (всё в одной функции). Для GCC более вероятен эффект.

**Риск.** Минимальный: если инвариант нарушен, debug-сборка даёт assert вместо молчания. No behavioral change in release.

**Метрика.** Сравнить медиану `h8_lf`, `h32_lf`, `h64_lf` до и после. Spread ≤1.8% для этих сценариев даёт надёжный сигнал.

**Тесты.** Весь существующий unit suite; Debug-сборка с assert. Этого достаточно.

---

### Эксперимент 2 — Value-only сканер после нахождения разделителя в `scan_header_line`

**Изменение.** В `sse2.hpp::scan_header_line` (аналогично avx2, swar): после того как `separator` найден и `key = false`, использовать `scan_header(p, end, false, literal)` вместо продолжения цикла `scan_header_line`. Это устраняет вычисление `colons` маски и dead-ветку для блоков значения.

Практически: после блока, в котором найден separator, выйти из текущего цикла и вернуть `{separator, scan_header(separator+1, end, false, literal)}`.

**Ожидаемый выигрыш.** Сокращение работы в value-фазе для длинных заголовков. Целевой сценарий — `long_1024`. Регрессия GCC/O3 +7.95% (held-out, spread ≤1.8%) — реальный сигнал.

**Риск.** Разрыв между separator и stop теперь из двух вызовов сканера вместо одного. Проверить, что `scan_header` с `key=false` имеет идентичную семантику с `scan_header_line` в value-фазе: да, `scan_header(p, end, false, literal)` останавливается на `\0, \n, \r, \\` (и на `:` если `!literal`, что правильно для value).

**Метрика.** `long_1024` и `long_128` как основные; `h8_lf`, `h32_lf` как контроль на регрессию коротких.

**Тесты.** Существующий full scanner correctness suite (`scan_backend_checks.hpp`) покрывает обе стороны страницы и все позиции событий — достаточен.

---

### Эксперимент 3 — `hdrline=ON` как default: разрыв между prePGO и PGO регрессиями

**Изменение.** Включить `STOMPTALK_EXPERIMENT_HEADER_LINE=ON` по умолчанию и повторить PGO-матрицу с теми же training/held-out scenarios.

**Цель.** Измерить: насколько PGO смягчает ранее зафиксированную регрессию `long_1024` у hdrline (pre-PGO: +33.71% GCC/O3; current PGO: +7.95%). Текущая матрица не является сравнением `hdrline+PGO` vs `split+PGO` — это сравнение `hdrline+PGO` vs `hdrline` без PGO. Это не отвечает на вопрос, стоит ли hdrline включать.

**Ожидаемый результат.** Либо PGO достаточно компенсирует long_1024 регрессию (и hdrline можно включить по умолчанию), либо нет (остаётся experimental).

**Риск.** Дорогой по времени эксперимент (полная PGO-матрица). Минимальное изменение кода — только CMake default.

**Метрика.** Обязательно сравнивать `long_1024`, `long_128`, `h64_lf`, `h64_crlf` между вариантами `split/plain`, `split/PGO`, `hdrline/plain`, `hdrline/PGO`.

**Тесты.** Существующий unit suite, **плюс** компиляция `fuzz_v2.cpp` с флагом для покрытия hdrline-пути в fuzzer-е.

## 5. Пробелы корректности / fuzz / corpus и оценка PGO

### Отсутствующие тесты

Все перечисленные ниже — конкретные input/schedule/expected, не утверждения о запусках.

**Gap-1: пустое значение заголовка** (не нашёл в `unit_v2.cpp`).  
Input: `"SEND\nkey:\n\n\0"` (7 байт).  
Expected: один кадр `SEND`, один header `{"key", ""}`, тело пустое, complete=true.  
Schedule: cut=1..len (функция `variants`). Важно проверить split именно на `:` и на `\n`.

**Gap-2: `content-length` в первом заголовке при LF в предыдущем чанке.**  
Input split: чанк 1 = `"SEND\n"`, чанк 2 = `"content-length:3\n\nhii\0"`.  
Expected: 16-байтный wire-путь НЕ используется (LF в предыдущем чанке, `curr == begin_` на старте чанка 2), parser корректно даёт `content-length=3`.  
Это проверяет именно условие `curr > begin_` на границе чанков.

**Gap-3: регрессионный тест для send_length_byte** (байт за байтом, SEND с content-length).  
Input: `"SEND\ncontent-length:5\n\nhello\0"`, chunk=1.  
Expected: один полный кадр, body=`"hello"`.  
Цель: regression guard для PGO-регрессии +11.21% (GCC/O2). Тест не измеряет скорость, но обнаружит семантические ломки.

**Gap-4: hdrline fuzz.**  
Существующий `fuzz_v2.cpp` не тестирует `hdrline=ON`. Нужна отдельная compile-time сборка с `-DSTOMPTALK_EXPERIMENT_HEADER_LINE=ON` для того же `LLVMFuzzerTestOneInput`. Corpus `v2/` покрывает все edge-cases по данным, но не этот code-path.

### Уже покрытые вещи (не повторяю как замечания)

`scan_backend_checks.hpp` покрывает guard pages с обеих сторон (0..129 байт, `mprotect(PROT_NONE)` с обеих сторон), все позиции специальных байтов, literal-режим, borrow в zero_mask. Это достаточно.  
`name_backend_checks.hpp` покрывает пустой view и guard pages на все словарные имена.  
`unit_v2.cpp` разбивает каждый тест во всех позициях среза — это сильная гарантия fragmentation correctness.

### Оценка PGO

**Качество профиля.** GCC: профили двух parser TU полностью сбрасываются и перезаписываются нагрузкой; unit coverage cold paths учитывается только в методах вне этих TU. Clang: IR raw-профили unit включаются в merge, но parser TU набирают счётчики миллионами кадров — unit-профиль в них потонет. Оба подхода корректны и задокументированы.

**Held-out результаты.** Три подтверждённые регрессии:
- `send_length_byte` GCC/O2 +11.21%, Clang/O3 +8.56% (spread ≤0.85%) — реальная регрессия
- `long_1024` GCC/O3 +7.95% (spread ≤1.80%) — реальная регрессия  
- `h0_lf` GCC/O3 +11.16% (spread ≤1.24%) — реальная регрессия

Все три — held-out, и у первых двух понятная причина: `send_length_byte` не было в training; `long_1024` — эффект hdrline combined scanner в value-фазе.

**Код Clang PGO.** +75% .text (43K→75K, 45K→80K байт). По профилю 90% семплов в `hdrline_done` — результат агрессивного inlining. Для I-cache-чувствительного серверного сценария это может быть нейтральным или отрицательным. Синтетический benchmark не отражает конкуренцию за I-cache с другим кодом.

**GCC/O2 spread 13%.** Пять повторов с 13% spread недостаточны для различения изменений меньше 5–7%. Для GCC/O2 результаты являются ориентировочными, не доказательными.

**Вывод по PGO.** Выигрыш реален на тренировочном workload-е; сервер с другим распределением заголовков получит меньший выигрыш и, возможно, другие регрессии. PGO-профиль нужно периодически обновлять на реальном трафике. Включать PGO и hdrline по умолчанию целесообразно только после Эксперимента 3.
