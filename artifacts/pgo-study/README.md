# PGO — GCC 16.2.1, O3, текущая v2

Исходники parser совпадают с этапом 4; меняются только compiler flags и профиль.
Сравнение с обычной GCC 16/O3 сборкой из общей матрицы. Один CPU 2, PIC, без LTO.
Обучение и benchmark идут последовательно; source и profile SHA256 сохранены.

## Обучение и проверка

`-fprofile-generate=<dir>` → смешанная нагрузка → `-fprofile-use=<dir>`.
Сборка use выполнена с `-Werror=coverage-mismatch -Werror=missing-profile`.
Profile-use ошибок/пропущенных файлов нет. Совпадают полезные счётчики всех
измерений. Итоговый CTest прошёл со штатным лимитом стека.

Обучение: purestomp 5 млн кадров SSE2, 5 млн AVX2, по 1 млн scalar/SWAR;
по 10000 итераций h8_lf, long_128, escaped, literal, fragment_chunk_7,
body64k_markers для SSE2 и AVX2. Остальные сценарии (включая byte input,
64 headers и значения 1024) не участвовали напрямую в обучении.
Для создания профилей test/classifier TU сначала запускается unit suite;
счётчики трёх parser TU после неё удалены, до представительной тренировки.

Первый инструментированный unit-запуск упал при обычном стеке 8 МиБ. Тот же
бинарник прошёл все 11056 streams / 2586117 checks с 64 МиБ. Для последующего
обучающего unit-процесса лимит поднят локально; production parser и use-бинарник
не менялись. Конечная use-сборка прошла тот же длинный tailcall test со штатным
стеком. Поэтому результаты generate не выдаются за производительность use;
инструментирование меняет поведение рекурсивной цепочки.

## Результат

100 млн кадров, GNU time, три чередующихся пары, медианы real/user/sys:

| Backend | Без PGO | С PGO | Δ real |
| --- | ---: | ---: | ---: |
| 3 | 6.74 / 6.73 / 0.00 | 6.08 / 6.07 / 0.00 | -9.79% |
| 4 | 7.34 / 7.33 / 0.00 | 6.11 / 6.10 / 0.00 | -16.76% |

.text PGO purestomp: **48992 байт**. Число само по себе не доказывает I-cache
причину ускорения. В профилях нет lost samples.

PGO улучшает и часть неучаствовавших сценариев: byte input SSE2
1531.90 → 1281.77 нс, 64 CRLF headers 840.52 → 695.36 нс. Есть регрессии:
16 значений по 1024 байта SSE2 1031.91 → 1061.25 нс (+2.84%),
AVX2 720.57 → 767.73 нс (+6.54%); escaped/AVX2 около +5.54%.
Улучшение purestomp не означает универсально лучший профиль.

Это измерение **GCC 16/O3 PGO**, не Clang PGO и не PGO всех уровней оптимизации.
Профиль из синтетики не становится настройкой библиотеки по умолчанию.
Для серверного варианта лучше обучать на реальном RPC и проверять отдельно
необучавшиеся сценарии. Публичный API и логика parser остаются прежними.

## Как применить профиль

Готовый профиль подставляется компилятору при пересборке через
`-fprofile-use=<каталог>`; во время исполнения готовой библиотеке он не нужен.
Наш каталог — `runs/20261027T173151930462Z/profiles/`. Use-сборка из этого
запуска уже готова в `runs/20261027T173151930462Z/build/`.
Для воспроизведения всех команд используется `run.py` с двумя аргументами:
каталог завершённого stage-4 запуска и каталог `gcc16-O3-v2` общей матрицы.

Сохранять фреймы необязательно: generate-сборку можно нагрузить прямо в
тестовом сервере и корректно завершить процесс для записи счётчиков. Если
нужен повторяемый replay, хранить последовательности байт по соединению и
размеры входных порций. Границы execute и настройки parser тоже влияют на пути.

В этой проверенной схеме generate/use используют тот же GCC, исходники,
оптимизацию и build path. Файлы GCC .gcda привязаны к именам объектов/путям;
перенос только каталога профиля в произвольный build не гарантирует его нахождения.
Несовпадение/отсутствие профиля остаётся ошибкой сборки. Профиль GCC не является
входом для обычного instrumentation-PGO Clang. [Правила GCC profile-use](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html#index-fprofile-use).
