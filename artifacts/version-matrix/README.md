# Четыре версии × три оптимизации × два компилятора

Машина: i7-12700K, CPU 2, powersave. GCC 16.2.1 (20260926) и Clang 23.1.4,
установленные локально; системный GCC 15.3 не переключался. Static PIC, без LTO
и -march=native. Для 1.2.2 нужен C++17, для остальных C++14. Код старых parser
взят из git archive и не исправлялся; собираются их исходные core TU.
C++17 virtual-hook adapter нужен для 1.2.2, C callback adapter — 1.7/1.8,
C result consumer — v2. Это скорость parser + полезного потребления результатов,
а не изолированные циклы сканирования. Накладные расходы разных API включены.

Снимки: 1.2.2 `6979c47b909ab4a32e1372d30b1577d230bfbda8`,
1.7.0 `10dc8cfa1fafdbccaec105f287e1d21b849dd72d`,
1.8.0 `54a926c34c4fa6274357d2683920125a5bbfb1b3`.
v2 — точный snapshot этапа 4, до PGO. 1.3.1 остаётся серверным baseline;
в согласованные четыре версии этой матрицы включена 1.7.0 как источник записи
о 12 млн/с. Хэши всех источников в run.json, проверены после сборок/измерений.

Каждая ячейка: 10 млн кадров (1 млн пакетов по 10 кадров), прогрев и пять
повторов с ротацией пяти вариантов. Аллокация/загрузка файла вне таймера.
Проверяются consumed, completed, headers, body_bytes, CONNECTED и JSON.
На пакет: 838 байт, 10 кадров, 35 заголовков, 67 body bytes, один CONNECTED
и один application/json. GCC/Clang CTest v2 прошли во всех трёх оптимизациях.

## Точные байты старого purestomp

Массив из `purestomp/main.c` совпал побайтно с нынешним `test/purestomp.c`.
На этом потоке совпадают полезные счётчики, но старые версии без escaping
сохраняют escape-последовательности как текст, а v2/1.8 их декодируют. Поэтому
здесь равен вход, но не вся семантика неизвестных key/value. Это дополнительная
работа новых версий, не ошибка ускоренного пути. Секунды на 10 млн кадров:

| Компилятор | Flags | 1.2.2 | 1.7.0 | 1.8.0 | v2 SSE2 | v2 AVX2 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| gcc16 | -Os | 1.7219 | 2.1927 | 1.5415 | 0.9555 | 0.9607 |
| gcc16 | -O2 | 0.9731 | 1.5836 | 1.2186 | 0.7055 | 0.6814 |
| gcc16 | -O3 | 1.0382 | 1.5132 | 1.2087 | 0.6793 | 0.7685 |
| clang23 | -Os | 1.2074 | 1.3885 | 1.3753 | 0.7657 | 0.8534 |

Разброс (max−min)/median старых версий местами достигает 18%; небольшие различия

0.3–2.2%. Медианы/все повторы сохранены; выбросы не удалялись. Существенное
преимущество v2 в этих потоках больше наблюдаемого разброса. Это не прогноз RPC/s.

## Неизменённый старый C-тест

Сам `purestomp/main.c` без правок дополнительно собран с 1.7.0, а нынешний
`test/purestomp.c` — с v2/SSE2. Это отдельный контроль исторического harness:
там глобальные counters вместо context getter в callbacks, нет счётчика всех
headers и отличается цикл потребителя. 100 млн кадров, O3, прогрев + три пары,
GNU time real/user/sys (секунды):

| Компилятор | 1.7.0 real/user/sys | v2 SSE2 real/user/sys |
| --- | ---: | ---: |
| gcc16 | 14.61 / 14.59 / 0.00 | 6.66 / 6.65 / 0.00 |
| clang23 | 12.56 / 12.55 / 0.00 | 5.16 / 5.16 / 0.00 |

Комментарий старого теста действительно содержит **v1.7.0, 100 млн кадров,
8.351 с**, то есть 11.97 млн/с. Его точный compiler, flags и commit не записаны;
версия в строке не доказывает соответствия git tag. На текущем PIC-контроле
результат не воспроизвёлся. Это не доказательство, что виноват новый compiler.
[Зафиксированный старый тест и SHA256](historical-test.json).

Дополнительные O3-сценарии: 64 CRLF headers, значения 128/1024 байта,
бинарное тело 64 КиБ с ложными маркерами и ASCII-поток порциями по семь байт.
Их counters совпали у всех версий; отдельные результаты в scenarios.csv.

должен проверяться отдельно, включая стоимость адаптера и очередей.

## Дополнительные проверки методики

Все **30 backend/opt/compiler сочетаний** профилированы (v2 имеет SSE2 и AVX2).
Это 24 version/opt/compiler ячейки плюс шесть вторых v2-backend. Во всех профилях
lost samples = 0. [Топ пяти](runs/20261027T171856326677Z/top-functions.csv),
[cycles/instructions/branches/branch-misses на кадр](runs/20261027T171856326677Z/perf-counters.csv),
[доснятые Os/O2](runs/20261027T171856326677Z/profiles-extra/run.json).

Generic C probe использует get_hook_arg, тогда как старый C-тест — глобальные
counters. Это измерено отдельно на тех же библиотеках GCC 16/O3: в первом
контроле context → global составило 1.51 → 1.33 с для 1.7.0 и 1.18 → 1.06 с
для 1.8.0 на 10 млн кадров. Часть затрат относится к consumer, а не к scanner.
Поэтому исходный C-test приведён отдельно, а API-adapter costs не скрыты.
Одинаковые счётчики не означают одинаковую последовательность инструкций клиента.

Дополнительно проверена старая static-сборка 1.7.0 без явного -fPIC, как в её
CMake. Исходный C-тест сокращён только до 1 млн итераций (10 млн кадров):
GCC 16 PIC 1.454 → compiler-default 1.355 с; Clang 23 1.256 → 1.245 с.
Вариация отдельных старых запусков заметна, особенно GCC-default; это не
доказательство единственной причины исторических 8.351 с. Они не воспроизвелись
и в таком контроле. [Сырые данные PIC](runs/20261027T171856326677Z/pic-check/run.json).

Нагрузочный тест многократно повторяет один набор кадров в одном parser.
Это полезный воспроизводимый контроль, но благоприятный для предсказания ветвей
и локальности данных. Он не моделирует очереди, владение сообщениями и сеть.
Реальные RPC-смеси, задержки и долю CPU надо измерять серверной команде.

## Почему выделяется 1.2.2 / GCC / O2

Дополнительный разбор уже полученных результатов, без новых замеров и без
изменения исходников. На original wire 1.2.2/O2 даёт 10.28 млн/с против
9.63 у O3 и 5.81 у Os. Она также быстрее 1.8.0/O2 (8.21 млн/с) примерно
на 25% по throughput, но имеет другой API и не декодирует escaping.

Пять O2-повторов: 0.97309, 0.95787, 0.96584, 0.98551, 0.97469 с.
O3: 1.02313, 1.03044, 1.03815, 1.04411, 1.08599 с. В этих выборках
диапазоны не пересекаются; уровни оптимизации измерялись разными сериями,
поэтому это ещё не отдельный чередующийся контроль O2 против O3.

У Os stackbuf::push остался внешним вызовом: около 62.01% sampled self CPU
приходится на него. В O2/O3 вызов встроен в header key/value states;
это подтверждено дизассемблированием. У Os около 2582 исполненных инструкций
на кадр, у O2/O3 около 1900; профили сняты на общей ASCII-смеси.
Это конкретное объяснение части отличия Os, но не доказательство всей причины.

Для O2/O3 соответственно: 1900.29 / 1900.17 instructions/frame,
457.96 / 508.80 cycles/frame, 0.321 / 0.331 branch-misses/frame.
То есть меньшим числом инструкций преимущество O2 не объясняется.
.text executable с consumer: 13510 / 13766 байт. Разница в размере невелика;
утверждать причину в I-cache по этим данным нельзя. Возможное влияние
расположения кода требует отдельного контролируемого эксперимента.
[Дизассемблирование и сводка](runs/20261027T171856326677Z/v122-analysis/assembly-summary.json).
